# Adopt merged machinery (prosthetic)

## Purpose
The `adopt-merged` skill ensures that a merged fix to the PR-landing machinery runs only when the installed copy is the merged version. It manages installed copies including the installed omni plugin tree (the `installPath` that `installed_plugins.json` names under `~/.claude/plugins/cache/private-repo/omni/<version>`; a live session keeps the tree it started with until it restarts), the marketplace clone new sessions install from, launchd tools copied under `~/.omninode` (pr-watcher lib, friction-rollup, drain-watchdog, ledger-publish), the `gh` shim copied into the lanes-only `~/.local/share/omni/lane-bin` (OMN-19856), and a worktree the drain is pointed at (the lab-pool driver). Canonical clones are fast-forwarded by the separate `canonical-clone-sync` launchd tick; this skill only reports a clone that has not caught up.

## Execution
`adopt_merged.py run` (the hourly `ai.omninode.adopt-merged` launchd tick calls it through `morning_workflows_tick.sh adopt-merged`; or call it by hand) runs one slice. The script prints `ADOPTION-TIMING scan_s=N converge_s=N rows_s=N rows=N deferred=N`, then `ADOPTION: prs=N pending=N converged=N drift=N (class=n ...) restart=... errors=N slice=complete` or `slice=partial deferred=N`. Dry-run omits the slice cell and ends with `dry-run`. There is no polling lane and no GitHub API reads; it reads `origin/<branch>` refs of the canonical clones and the installed files.

The slice budget is `--budget-s`, else a non-negative `ONEX_ADOPT_BUDGET_S`, else two thirds of a positive `ONEX_MORNING_MAX_RUNTIME_S` (900 seconds gives 600), else unlimited. Invalid environment values fall through; zero means unlimited. After scan and convergence, the row phase gets the remaining budget or at least 60 seconds. `--max-prs` caps per-PR rows per slice (zero means no cap). `--rows-per-append` (default 25) is how many rows one ledger append writes: each append takes the ledger lock and reads the whole ledger, so one append per row cost about 7.5 seconds a row (OMN-17427). Dry-run never defers. `last_run` is the finish of a slice, including a partial one; stored slice data records its start, finish, rows, deferred count and elapsed seconds. `status` adds `slice=complete|partial deferred=N` and `unfinished_since=<last_start>` when a newer start has no finish.

## Exit code (OMN-20854)
`run` exits 0, except 3 when something is held back: a blocking-class finding (`stale`, `missing`, `superseded`, `clone-behind`, `held`, `controller-off-main`) present for two consecutive completed runs. An error alone (`errors>0`) no longer fails the run (OMN-17427): it is printed as `ADOPTION-ERROR` and carried in the run event, and an error that does hold a file back (an installer that failed) leaves that file's `stale` or `missing` finding, which counts. A completed run is one that reached its end, a partial slice included; a `--dry-run` and a `BUSY` run exit 0 and count nothing. `unmerged` and `refused` do not count: they have their own owners. The state file keeps `blocking`, one record per finding with `first_seen` and `runs`; a finding that is gone from a run is dropped, so a finding that comes back starts at one. The `ADOPTION:` line carries `persisting=N`, and a failing run ends with one `ADOPTION-FAILED exit=3 persisting=N errors=N ...` line naming the five oldest persisting findings, each with `since`, `runs` and its remedy. `status` prints `persisting=N` too. The morning tick maps a non-zero exit to a `failed` fire receipt, which the host observer reads as a failed run.

Every completed run (not a `--dry-run`, not a `BUSY` run) appends one event to `events.jsonl` beside the state file and prints it as one `ADOPTION-EVENT {json}` line (OMN-17427): `ts`, `host`, `exit`, `prs`, `pending`, `installed` (each copy written, installer run, fast-forward or plugin update), `held` (every blocking finding with `first_seen` and `runs`, at most 200; `held_count` is whole), `persisting`, `errors` and the drift `summary`. The newest line's `ts` is the run record a liveness reader ages.

The failure is also written to the ledger (OMN-20863): the first run with a persisting finding appends one `FRICTION | lane=adopt-merged | ticket=OMN-20863 | class=adoption-persisting | episode=<opened> | persisting=N | cost=est <hours since the oldest finding was first seen> ...` row, and prints `ADOPTION-FRICTION <append result>`. A later run appends another row when a persisting finding the episode's last row did not name persists: a new one, or one that cleared and returned inside the open episode (OMN-24643); the row names the new findings first, then the oldest (five in all), and its cost counts the hours since the previous row, so the friction rollup's sum counts each hour once. A run whose persisting set the last row already named appends none until a completed run with nothing persisting ends the episode; a refused append is retried on the next failing run. The state keeps the episode as `friction_episode` (`opened`, `row_at`, `row_keys`: the keys the last row named that still persist; an episode from before `row_keys` existed counts the findings first seen before its `row_at` as named), and `status` adds `friction_row=<when|unwritten> episode_since=<opened>` while one is open.

## Commands
- `python3 ${CLAUDE_SKILL_DIR}/scripts/adopt_merged.py run [--dry-run] [--since ISO] [--verbose] [--no-converge] [--budget-s FLOAT] [--max-prs INT] [--rows-per-append INT]`
- `drift [--json]`: Read-only scan.
- `status`: Prints one stored line, which is what `queue-status` prints on its adopt line.
- `install-tree`, `verify-installed`, `smoke-tree`: the tested install with rollback (below).
- `backups --since ISO [--json]`: Lists every `*.bak*` backup newer than ISO next to an installed copy, with the live file's class. This is the hot-patch reconciliation list.

## Installed Targets
For installed targets with an installer, the installer is rerun when a merged file of the copy is behind and the canonical clone's working tree already holds the merged files. An unmerged file (a hot-patch from an open pull request) holds only itself (OMN-20863): the installers replace the copy whole and cannot skip one file, so each unmerged file and its `.bak*` backups are read before the installer runs and written back after it, also when it fails. The run prints one `ADOPTION-PARTIAL <target> <copy>: installed N merged file(s); held M unmerged in place: <path> in=open-pr:<repo#n>; ...` line (`would install` / `would hold` on a dry run). A held file the run could not write back counts as an error.

A target may list `defer_while_running` (argv substrings). While any is found in the process list, or the list cannot be read, the installer waits for the next pass and the run prints `ADOPTION-DEFERRED <target>: installer deferred: in-flight ...` (`worktree-triage-lib` uses it for the triage runner, OMN-24661; no other registry target has since OMN-17427: `morning-workflows-lib` runs `morning_trigger_install.sh --lib-only`, which swaps the lib through one rename and reloads no label; the earlier `--new-agents-only` booted out every interval label, `ai.omninode.adopt-merged` among them, so from adopt-merged's own job it stopped the job running it). The morning installer reads only its first argument, so a target names exactly one mode flag. The match leaves out this run: the process, its ancestors and descendants, and the whole tree of the outermost ancestor that matches a pattern, because the tick forks watchdog subshells beside the adopt-merged child that are copies of the tick script (OMN-20780). A tick of another workflow still defers it.
A `installed` target may list `only_if_exists` (paths): the target compares nothing where any of them is absent, so a Linux lab host that holds a launchd unit's lib path but no plist reads no drift and runs no launchd installer (`worktree-triage-lib`, `friction-rollup`, `omnimarket-release-cut-lib`; OMN-24661). `unit_roots` in the registry maps every installed copy a unit runs under `~/.omninode` to the target that compares it or to `gap: <reason>`; `tests/test_unit_roots_have_targets.py` reads the roots from the installed `ai.omninode.*` launchd plists and fails when one is under no key (`_out_of_scope` names the copies not compared, with the reason; OMN-24682). The targets `internal-clone-sync-lib`, `host-drift-lib`, `host-drift-sync-lib`, `omnimarket-release-cut-lib`, `session-tick-runner` and `worktree-triage-lib` are report-only (`adopt: false`): their units belong to the host installers, which this check does not run. A report-only finding, its FRICTION row and the `ADOPTION-FAILED` line name the unit's own installer, the first backticked installer command of the target's `_note`, never the class remedy (OMN-24682). A symlink in the repository compares as the file it names, since an installer copies it dereferenced (OMN-24682).

## Plugin update guard (OMN-19852)
Before the marketplace target updates the installed plugin, the candidate tree at the marketplace ref is checked in git against the union of its own `hotpatch_markers.json` and the installed version's (`scripts/plugin_guard.py`, the same marker rule `merge_pulse.py` reads). A missing marker refuses the update. A pull request that hot-patches an installed copy adds its marker entry in the same PR, so the fix cannot be dropped by a version switch. `plugin_guard.py check|pin|verify-pin` is also what the merge drain launches from (merge-drain SKILL.md, section 8).

## Install canary and rollback (OMN-17427)
On 2026-10-17 plugin 0.4.424 passed its own tests, installed, and refused every lab host (`clone ops_tooling_pkg is missing from the registry root`); every rollback was a hand hot-patch. The marketplace target's `canary` (in `adoption_targets.json`) makes this host the canary. Right after `update_command` installs a version, each step in `canary.steps` runs in order, with `{plugin_root}` set to the installed version's directory and `{python}` set to this interpreter:

- `pool-admit`: `adopt_merged.py canary-pool` from the new version reads the pool with a remote lane's parity needs and the clones the usual lanes are built from (`--repo`, default ops_tooling_pkg, plugin-tooling-pkg and omniclaude). It exits 1 when fewer than `--min-admitted` (default 1) lab hosts admit. A load, memory or link refusal still counts as admitting; a parity or hook-parse refusal, or an unreadable host, does not.
- `controller-loads`: the new version's `landing_controller.py status` (the whole module imports).
- `pr-watcher-fresh`: the new version's `pr_state_local.py --status` (exit 3 on a stale watcher state).

The steps run from the candidate's own tree (OMN-22388). A cache version directory is named for the version and a merge that does not bump it installs under a name that exists: `update_command` leaves that directory as it is, holding the first commit installed under the name. On 2026-11-04 five candidates labelled 0.4.467 were canaried against the bump commit's tree, so the fleet-reading rule of #1540 never ran and a candidate's own fault could not fail. The canary compares the installed directory with the candidate commit's tree (the comparison `install-tree` makes); when they differ it builds the candidate's tree from the commit into a scratch directory under the same version name, runs every step from it with `ONEX_CANARY_INSTALL_ROOT` naming the installed directory (so the pool read finds the previous version beside it), and removes it. The record and the event carry `tree`: `installed` or `built`. A tree that cannot be built runs from the installed directory and says why in `tree`.

All steps pass: the record (`canary.record`, default `$registry_root/.claude_scratch/adoption/canary.json`) names the commit and version as `passed`. One fails (non-zero, timeout or unrunnable): `installed_plugins.json` gets its pre-update bytes back, the marketplace clone is reset to its previous commit with `git reset --keep` (a local modification survives, or the reset refuses and is an error), and the record names the commit as `failed` along with every step's exit and output tail. One `canary-fix-<sha10>` lane is queued in the remote-lane queue that the throughput tick starts (`landing_placement.lane_queue_enqueue`), with a brief beside the record that carries the smoke output. Every canary appends one `{"kind":"canary",...}` line to `events.jsonl` beside the record and prints it as `ADOPTION-CANARY {json}`.

While the plugin's merged tip is the failed commit, the plugin-cache target that names the same record (`canary_record`) copies nothing into the live cache versions and reports `canary-failed`, so the copy step does not hand a rolled-back host the failed files. It does not yet hold back the copies of a new merge that land before any canary has run, nor a merge that does not change the version, which `update_command` never installs and so never canaries. A failed commit is never installed again: later runs report `canary-failed` (blocking, so the second completed run exits 3) and send one `ADOPTION-RED: plugin install canary failed` MSG per failed commit. The next merge gets its own canary. A step that declares `baseline_control` (pool-admit) is re-run from the previous installed version when it fails: if that version fails the same way, the pool was not read and the candidate is unproven, so nothing rolls back (the marketplace clone holds every plugin at one HEAD, and a rollback to the pin drops overlays such as `cloud_fill`), nothing is recorded `passed`, the lab is shipped nothing newer, and the `canary-unproven` action quotes the `CANARY-POOL` lines. A candidate that fails where the previous version passes rolls back as before. Lab lanes are shipped only the commit the record names as `passed` (`onex_remote_lane.canary_cap`). With no record the merged tip ships as before, and an unreadable record, or one with no passed commit, ships nothing newer than the marketplace commit. Not yet steps: a no-op lane that places and finishes, and a throughput tick. Each has side effects, and the tick starts queued lanes.

## Script and source are one merge (OMN-20497)
On 2026-10-18 the cache's `session-start/scripts/throughput_tick.py` carried the merge that calls `HandlerProcessFixOwnership` while the cache's `src/plugin_tooling_pkg/.../handler.py` was the older merge, and the tick died with an `AttributeError`: the cache target's `source_prefixes` named `src/omni/` and never `src/plugin_tooling_pkg/`, so adoption copied the script and not the source it imports. Guards close that:

- **The registry names every package.** `tests/test_atomic_adoption.py` fails when the cache or marketplace target omits a directory under the repository's `src/`.
- **A copied set installs whole.** The copy scan resolves the target ref to one commit and reads the tree, its history and the superseded check from it, so every file of a copy comes from that commit. The merged blobs are read first, every file is staged beside its destination, then swapped in with the source under `src/` ahead of the scripts that import it. A read, staging or swap failure puts back each file already swapped and prints `ADOPTION-ERROR <target> <copy>: nothing installed: ...`; the files stay `stale` (blocking) and the next pass retries. If a swapped file cannot be put back the error says `PARTIAL install ... not put back: ...`. Files held for an unmerged hot-patch stay out of the set, as before.
- **The installed plugin tree is never a set of copied files.** A script and the source it imports come from one commit because the whole tree is built from one commit (next section). The copy guards above still serve the targets that are copied file by file.

## Tested install with rollback (OMN-20497)
On 2026-10-18 a merged script was copied into the installed plugin twice without what it imports (`throughput_tick` AttributeError at ~21:35Z, `landing_facts` ModuleNotFoundError at ~23:26Z, which broke every remote-lane dispatch). The hand fix built the plugin from one commit, smoke-tested it before and after and kept the old tree; it missed `.claude-plugin/plugin.json` and placement's parity check refused a host for it. `node_plugin_tree_install_effect` (`src/omni/nodes/`) is that fix as the install path:

- **The smoke suite is generated from the tree.** For every `skills/*/scripts/*.py` a fresh interpreter (no `PYTHONPATH`) loads the script as a module, imports every module it names anywhere in its body (a dotted name of another repository's package is that venv's to supply), checks each `from M import N` name and each attribute it reads off a module of the tree; an import inside `try ... except ImportError` or `if TYPE_CHECKING` is optional. A script with an argparse main also runs `--help`. On this repository's tree that is 119 checks, about 3 s.
- **`install-tree --branch <b> | --commit <sha> [--clone] [--version-dir] [--dry-run]`** builds the tree whole from one commit (`git archive`: every file and dotfile; `src -> ../../src` copied in as the installer does), checks it equal to the commit's tree with the comparison placement's parity check makes (`__pycache__`, `.in_use/` and bytecode left out), smokes it, renames the installed tree to `<version>.rollback-<stamp>` and the staged one in, sets `gitCommitSha` in `installed_plugins.json`, and checks and smokes again. A staged failure installs nothing (`refused`); an installed failure renames the previous tree and the manifest back (`rolled-back`). `--branch` reads `origin/<b>` in the clone, so a fix installs before its version bump lands. The newest three kept trees stay.
- **Record clobber (OMN-22270).** Before it builds, `install-tree` reads the `gitCommitSha` of the `installed_plugins.json` entry for the tree. When the requested commit does not contain that revision, and the commits of the revision that no main holds (`origin/main`, `main`) are not carried by the requested tree (a commit whose changed files read the same in both is carried, as a squash merge is; so is one whose files differ only because main changed them again after the squash, when every line the commit added that the recorded revision still holds is in the requested tree's copy of the file), it refuses with `verdict=refused`, check `record-clobber`, the typed `ErrorPluginTreeRecordClobber` and the missing commits in `missing_commits` (ledger cell `missing=`); nothing is built or swapped, a dry run refuses too. On 2026-11-02 a second install from another base dropped plugin-tooling-pkg#1479, which the installed record carried. A commit that contains the record, a recorded revision on main and a record the clone does not know install as before. To install over a record on purpose, merge the recorded branch into the requested commit first. **`--with-installed` (OMN-23236)** does that merge for you: `install-tree --branch <b> --with-installed` installs one commit that holds the record and the branch (the branch itself when it already holds the record or the record is unknown to the clone, the record when it already holds the branch, else their merge made as `run` makes one with `git merge-tree` and `git commit-tree`, kept under `refs/tags/adopt-merged/`), so a lane's branch stacks on the install another lane left and the record's fixes are never dropped. A clash between the two refuses with check `with-installed` and names the files; nothing is installed. The refusal text of a record clobber names this flag.
- **`verify-installed`** smokes the installed tree and, on a failure, renames back the newest kept tree that passes and its commit; `run` calls it once an hour (`--no-tree-verify` skips it; the stamp is `plugin_tree.verified` beside `plugin_tree.json` in `$registry_root/.claude_scratch/adoption/`). `smoke-tree --root <dir>` is the suite alone; it is the marketplace canary's first step, so a version install is smoked after `update_command` and rolled back by the canary.
- **`run` adopts a merge through this install (OMN-17427).** See the next section.
- A `pass` row names the previous tree it kept in `kept=<version>.rollback-<stamp>`; only a `rolled-back` row (or a dry run) carries `restored=`, so a kept tree never reads as a rollback (OMN-21871).
- Every install, rollback and failed verify writes one `STATUS | lane=adopt-merged | ticket=OMN-20497 | ... | PLUGIN-TREE op=<op> | commit=<sha> | result=<verdict> | tree=<dir> | ...` row.

## Per PR Ledger
One ledger row is written: `STATUS | lane=adopt-merged | ... | ADOPTED pr=<repo#n> merge=<sha> | targets=... | drift=N | restart=...` once its copies hold the merged version. Immediately after the merge walk, cursors, all queued PRs and `last_start` are checkpointed before convergence and row appends. Rows are processed oldest first; a PR whose clone is behind or whose row is deferred by the slice stays pending for the next run. A killed run resumes from the saved cursor and queue. The row is written at most once per (PR, merge) pair across runs (OMN-20517): the pair stays pending and is saved as `adopting` before the append of its batch and as `adopted` after it, a pair a killed run left `adopting` is looked up on the ledger before any second append, and a second `run` while one holds `run.lock` beside the state file prints `ADOPTION: BUSY` and does nothing.

## Plugin tree adoption (OMN-17427)
On 2026-10-21 `adopt-merged` copied the changed `landing_g_act.py` of plugin-tooling-pkg#1081 into the tree `install-tree` had installed at 10:43Z from a local commit that is not on main (`2d8d3b1682fb`). The tree no longer equalled the revision `installed_plugins.json` records, and lab placement's parity check refused this host for every unit (`installed plugin omni differs from its shipped revision 2d8d3b1682fb: changed=1`). The file copy was also the cause of the 2026-10-18 breakages that `install-tree` replaced. The plugin-cache target no longer copies a file into the installed tree:

- **The commit to install holds both sides.** `run` reads the installed entry's `gitCommitSha` (its recorded revision) and the target's merged tip. When the revision is on main, the commit installed is the tip. When the revision already holds the tip, it is the revision. Otherwise (a local commit that is not on main) a merge commit of the two is made with `git merge-tree` and `git commit-tree` in the canonical clone, so neither its working tree, its index nor any hook is touched, and kept under `refs/tags/adopt-merged/<sha>` so the parity probe finds it. Its identity and dates come from the tip, so the same two parents make the same commit.
- **The install is `install-tree`'s.** `node_plugin_tree_install_effect` builds the tree whole from that commit, checks it equal to the commit, smokes it, swaps it in by rename, checks and smokes it again, sets `gitCommitSha` to the commit and rolls back on any failure. After a run the installed tree equals its recorded revision, which is what the parity check compares, so no `merged_since` allowance is needed.
- **A file that never merged holds the install.** A tree is replaced whole, so a hot-patch in it would be lost. Every file that would change is classed as before (`stale`, `missing`, `superseded`, `unmerged`); one `unmerged` file makes the plan `held`: nothing is installed and each differing file is reported (`held`, blocking, with the `unmerged` one beside it). A revision that conflicts with the tip is reported `stale` with the conflicting files named and nothing is installed. A recorded revision that no clone holds cannot be merged, so its files read `unmerged` and the install is held.
- **A dry run installs nothing** and names each file it would change as `would-copy`.
- **Only the installed tree is adopted.** Older version directories that live sessions still pin are left as they are; those sessions pick up the new tree when they restart. The restart rules read the pinned versions before the swap.
- **A branch install stays installed until its pull request merges or closes (OMN-19998).** On 2026-11-13 four branch installs (plugin-tooling-pkg#1882, #1860, #1876, #1878) were gone from the installed tree: `run` had updated the plugin to main's new version with `claude plugin update`, which installs a fresh tree from main and reads no record, and drift read 0 findings. Every successful `install-tree --branch <b>` now writes `branches[<b>] = {head, commit, at}` into the install record (`$registry_root/.claude_scratch/adoption/plugin_tree.json`; a `--commit` install, a refused or a dry-run install writes nothing). `run` keeps every recorded branch whose pull request the PR watcher reads as open or does not know: a head the installed tree lacks is merged in (`git merge-tree`, never settled in the branch's favour) and the new head is recorded. It drops a branch from the record when the PR watcher reads its pull request merged or closed, or its head is on main (the action `dropped-branch <b> (<why>)`); an unknown pull request is never read as merged. After a `claude plugin update` the plugin-cache target runs once more in the same run. A closed branch's commits already in the installed tree stay until the next install built from main; the record stops naming it. A recorded branch the tree lacks is drift class `lost`.
- **To put a merge on a host by hand:** `python3 ${CLAUDE_SKILL_DIR}/scripts/adopt_merged.py run` (or `--dry-run` first). To install a named commit or branch: `install-tree --commit <sha>` or `--branch <b>`, which is the same install.

## Restarts
A process that loaded a file at start must restart when the file changed under it. When a pass copies a file matching a restart rule:
- `none`: Reloads on its next launchd tick (e.g., pr-watcher).
- `kickstart`: `launchctl kickstart -k` of a KeepAlive agent marked safe (e.g., hook-emit-drainer).
- `msg`: One MSG row to the `parent=` lane of the newest drain-run CLAIM (e.g., to restart a long-running workflow after its script changed).
The same file set sends at most one action per hour.
